# Минимальный план внедрения и отката

**План, не выполненные действия.** Работающий сайт, main, Cloud Function, YDB и Telegram не изменялись. На каждый этап публикации необходимо отдельное разрешение; не предполагается создание новых сервисов. Юридические условия — [09](09-final-readiness-audit.md).

## 1. Отделить два выпуска

**Выпуск А — достоверные документы, без изменения протокола.** Может состояться раньше v2 после закрытия юридических условий: текущий v1 описан как legacy-технический пакет, а не полученное согласие; действительное основание обычной заявки установлено внутренним решением. Номер JSON-схемы законом не установлен. Нельзя публиковать служебные заглушки или писать, что v2 уже работает.

**Выпуск Б — совместимый v2, затем клиент.** Это отдельное изменение после реализации и проверок, а не условие, позволяющее бессрочно оставлять устаревшую политику. Не объединять скрыто с заменой схемы дедупликации, Telegram или CRM.

## 3. Последовательность

1. Закрыть Б1–Б4: правовые основания внешних потоков, факты/уведомления, доступ и минимизация, исполнимые права/удаление; зафиксировать ответственных. Проверка договора и лицензирования не заменяется отметкой «будет позже».
2. Зафиксировать точные версии публичных текстов и исходные SHA клиента/сервера, совместимость отката; сохранить утверждённые тексты вне изменяемой страницы. Служебная дата аудита не становится выдуманной датой вступления документов в силу.
3. Выпуск А: собрать только утверждённые документы и при необходимости ссылку. Локально проверить якоря, старые юридические URL, мобильную читаемость и отсутствие изменений запроса v1. Запросить разрешение на публикацию, затем проверить опубликованные тексты/ссылку.
4. Выпуск Б: сначала локально реализовать dual v1/v2 и совместимое хранение. Точно определить семантику первого получения/попытки: не обещать атомарное «самое первое время» при BulkUpsert без CAS. Сохранение новой метки не должно приводить к ложному отказу при повторе или перезаписи доказательств.
5. После локальных тестов и отдельного разрешения выполнить согласованную совместимую миграцию/развёртывание backend на существующих ресурсах. Старый клиент всё ещё работает. Не направлять реальную форму на неподтверждённый сервер.
6. Проверить v1 и v2 на синтетике, только затем отдельно согласовать выпуск клиента v2. Уже начатые попытки не переводить между протоколами; учитывать вкладки и кэш, не только новую загрузку.
7. После выпуска клиента проверить по одной синтетической заявке каждой школы и ошибки/повтор. Логи без контактов/токенов, связь проверки по requestId/receipt. Период поддержки v1 устанавливается по фактическим кэшам и старым попыткам, не произвольным обещанием «всё обновится сразу».

## 4. Минимальные проверки — пока не запускались

**Локально, с заглушками внешних систем:**
- v1 до/после обновления, v2 без consent; отклонение неизвестной версии/поля и отсутствующей или проваленной CAPTCHA;
- успех только после подтверждённого ReadRows, отказ/неопределённый исход сохранения, сетевой таймаут и повтор той же попытки;
- истечение допустимого возраста pending и расхождение часов: не ломать допустимые старые попытки и не выдавать неизвестный результат за успех;
- одинаковый пакет с обновлённым CAPTCHA даёт тот же receipt; серверное время не меняет ключ/детерминированную запись; изменённый бизнес-пакет имеет описанную семантику;
- сохранение v1 ключей и sent:-отметок; чтение строк без новых метаданных; сериализация новых необязательных типов официальным YDB SDK;
- никаких accepted:true/рекламных разрешений для v2; legacy v1 не становится доказательством согласия;
- сервер выбирает группу по филиалу, сбой Telegram не уничтожает lead, повтор доставки не создаёт новую основную заявку; ограничение конкурентных повторов сообщений честно остаётся;
- ссылка/якоря и старые URL, один оператор, отсутствие незаполненных служебных полей, неизменность видимого дизайна.

Ориентир профильного запуска после реализации: unittest для test_service и test_bulk_mvp из backend/yandex-leads/tests, node --test scripts/lead-client.test.mjs, сборка scripts/build_site.py и проверка scripts/check_site.py. Точные команды учитывать относительно импорта модулей; не заменять живой YDB-тест SQLite. Существующий обязательный CI при будущей публикации не обходить.

**После отдельного разрешения, на существующей инфраструктуре:** проверка реального сохранения/чтения обеих версий, затем браузерные Kaluga/Troitsk и маршрутизация групп. Только синтетические данные. Не устраивать нагрузку/спам для проверки дедупликации: один повтор той же попытки достаточен для сценария, но не доказывает строгую конкурентную уникальность.

**Мобильная регрессия:** открыть/закрыть форму, iPhone Safari и узкий экран, клавиатура/автозаполнение, внутренний скролл, доступный крестик; размеры и поля не менять. Проверка документов не требует повторного полного тестирования всех анимаций.

**Удаление:** отдельно проверить процедуру на синтетической записи и её sent:-копии/сообщении после разрешения; зафиксировать акт/журнал по применимым требованиям. Не удалять реальные заявки ради теста. Для старых Telegram-сообщений нельзя полагаться на deleteMessage бота: официальный API ограничивает возраст менее 48 часов. Ручное удаление уполномоченным администратором/иной допустимый способ сначала проверяется отдельно; само наличие прав бота не доказывает возможность удалить старую копию.

## 5. Откат

- При ошибке клиента v2 вернуть предыдущий клиент, **оставив dual-сервер**. Открытые v2-вкладки продолжают обращаться к нему. Нельзя возвращать v1-only сервер, пока такие запросы возможны.
- При проблеме backend до выпуска клиента остановить выпуск Б, сохранить работающий v1 и все данные. Новые необязательные поля не удалять; не откатывать через восстановление старой копии поверх новых заявок.
- Для документов откатить ошибочный текст/ссылки на последний **достоверный утверждённый** вариант. Старую заведомо неверную декларацию «данные не сохраняются» не считать юридически безопасным откатом; можно отдельно выпустить исправление текста, не трогая приём.
- По сохранённым receipt проверить неопределённые отправки перед повтором, использовать ту же pending-попытку. Не генерировать новый ID автоматически при сетевой ошибке.
- Старый Cloudflare Worker не включать автоматически: это другой поток и правовые условия. Для такого переключения требуется отдельное решение.
- Ошибка интерфейса не основание удалять данные, сбрасывать Telegram-маркеры или ослаблять SmartCaptcha.

**Результат этого этапа:** готов план, а не готовый v2 backend. Разрешений на миграцию, развёртывание, PR или публикацию этой задачей не получено.
