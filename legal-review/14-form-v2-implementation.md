# Решение по фамилии и готовая заготовка v1/v2

**Только review-артефакты. Рабочий frontend/backend не изменялся.** См. implementation/contract_v2_candidate.py и профильный test_contract_v2_candidate.py.

## 1. Решение по фамилии

Для ответа на первичную заявку на индивидуальное занятие не найдено специальной нормы, обязывающей собирать фамилию каждого заявителя. При текущей цели имя, телефон, школа и направление обеспечивают связь. Доказательств, что фамилия объективно необходима до первого контакта, в коде/материалах нет.

**Подготовленное решение: оставить поле и его дизайн, сделать фамилию необязательной в новом v2.** Пустое значение передаётся строкой ""; заполненное валидируется как сейчас. При дальнейшем договорном оформлении необходимая фамилия собирается на соответствующем основании. Добровольный ввод не считать универсальным согласием; использовать только в пределах заявки. Это устраняет неподтверждённую обязательность без удаления поля или галочек.

В v1 валидация не меняется: старые вкладки продолжают присылать обязательную фамилию. В v2 на той же странице поле остаётся, снимаются только HTML required и безусловная JS-проверка пустой фамилии. Если заполнено — 2–80 символов и прежние допустимые символы. Действующий сервер v1 не может принять пустую фамилию: порядок «сервер раньше клиента» обязателен.

## 2. Точный новый контракт

Обязательный полный набор ключей: schemaVersion, requestId, createdAt, name, surname, phone, branch, direction, website, pagePath, privacyNoticeVersion, captchaToken. surname может быть пустой строкой; direction при отсутствии выбора — unsure, website — пустая строка. Имя/телефон/школа остаются обязательными.

consent, accepted, рекламные разрешения и доверенный legalBasis в v2 отсутствуют. Неизвестные поля отклоняются. privacyNoticeVersion выбирается только из утверждённого сервером отображения «версия → URL/снимок». Тестовая версия fixture-notice-v2 не является опубликованной редакцией.

Подготовленный модуль:
- сохраняет прежний v1 валидатор и точный SHA-256/receipt без переканонизации;
- строго валидирует v2, включая соответствие школы странице и необязательную фамилию;
- исключает только CAPTCHA из бизнес-хеша, не включает серверное время;
- возвращает серверный проект метаданных: цель trial_lesson_request, основание 152-FZ:6:1:5, серверное время текущей попытки, версию схемы/уведомления; для v1 отдельная семантика legacy_unverified, без признания согласия;
- ничего не отправляет и не сохраняет. Это протестированная часть будущего адаптера, **не готовая к deploy функция** и не доказательство облачной совместимости.

Код основания применим только после утверждения матрицы реальных целей; он не разрешает поручение/Telegram автоматически. Метка времени означает текущую проверенную попытку, не обещание атомарного первого получения.

## 3. Конкретная интеграция после разрешения

1. service.py: вместо единственной проверки valid использовать подготовленную раздельную валидацию; сохранить Origin, Gateway-контекст, ограничения, rate-limit, серверную SmartCaptcha и путь /leads. Вызов подготовки бизнес-пакета после CAPTCHA; не менять URL и не переводить клиентов на новую архитектуру.
2. bulk_store.py: убрать предположение, что для каждой новой схемы есть data['consent']; записывать новый пакет без фабрикации accepted. Добавить согласованные nullable-метаданные правового основания/времени/версии, не класть их в поля consent_accepted_at. Для v2 старые поля согласия пустые/NULL; v1 остаётся legacy.
3. Сначала подготовить точную обратно совместимую схему YDB и SDK-типы, затем отдельно проверить на разрешённой синтетике. Старые строки без новых полей читаются; receipt и sent:-ключи не мигрируют.
4. Сохранение + ReadRows остаются условием успеха. Детерминированные поля и метаданные времени разделяются так, чтобы повтор не менял receipt, не перезаписывал сохранённое доказательство и не давал ложный отказ. Первичное время под конкурентной записью без CAS не обещать.
5. После dual-сервера: site/lead-form.js создаёт pending v2 без consent; site/lead-config.js задаёт утверждённую версию уведомления. Существующая pending-попытка не переводится между схемами. Ошибка сети не создаёт новый ID.
6. templates/lead-dialog.html: убрать required только у фамилии, сохранить прежнюю ссылку/дизайн. Ссылка ведёт к политике, надпись «Ваши данные в безопасности» не меняется; никаких галочек или рекламы.
7. site/lead-form.js: пустую фамилию разрешать только для нового v2; непустую проверять. Телефонная маска, клавиатура, фоновой скролл и модальные состояния остаются прежними.
8. Сначала подтвердить сохранение/чтение и уведомления обеих школ, затем отдельное разрешение публикации клиента. Откат клиента возможен при сохранении dual-сервера; v1-only сервер при живых v2-вкладках недопустим.

## 4. Проверки и пределы

Локальные тесты проверяют v1 неизменность, v2 без consent, необязательную фамилию, неизвестные поля/редакции, границы времени, соответствие филиала, неизменность входных данных и receipt при новом CAPTCHA/серверном времени. Они используют действующий Python-валидатор и stdlib, не SQLite и не имитацию совместимости YDB.

Слой хранения, необязательные YDB-типы, first-received семантика, реальная SmartCaptcha и Telegram в этом кандидате **не тестируются**. Они требуют следующего разрешённого этапа реализации; это осталось явным условием выпуска Б, а не скрытым обещанием готовности.

Ничего не мешает отдельно опубликовать достоверную политику после закрытия юридических условий, не меняя JSON v1. Старый accepted при этом не используется как доказательство согласия. Неподтверждённые внешние основания и удаление одной сменой схемы не устраняются.
