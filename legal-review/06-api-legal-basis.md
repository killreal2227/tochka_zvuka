# Проект изменения API и фиксации правового основания

**Документальная спецификация. Ни одна из описанных миграций или правок сейчас не выполняется.** Текущий frontend, backend, YDB и Telegram не изменяются.

## 1. Задача и действующее ограничение

Сейчас `schemaVersion=1` содержит обязательный объект `consent`, автоматическое `accepted:true`, клиентское время и старую версию согласия. Сервер проверяет точный набор полей. Простое удаление `consent`, замена его на `false` или добавление произвольного `legalBasis` нарушит работу.

Цель — регистрировать фактическую инициативную заявку и выбранное оператором законное основание, а не продолжать создавать фиктивное доказательство согласия. Для перехода нужны согласование модели по каждому этапу, версия протокола и совместимый порядок включения, без новых сервисов.

## 2. Предлагаемый контракт v2

Обычный запрос сохраняет бизнес-поля: `requestId`, `createdAt`, `name`, `surname`, `phone`, `branch`, `direction`, `website`, `pagePath` и `captchaToken`. Изменения:

- `schemaVersion: 2`.
- Объект `consent` отсутствует: нет `accepted`, времени/версии якобы полученного согласия.
- `privacyNoticeVersion` — идентификатор фактически предоставленного информационного текста. Это **не согласие и не подтверждение прочтения**. Значение утверждается при выпуске текста, не выдумывается в документации как уже действующее.
- Никаких рекламных флагов и контактов иных каналов в обычном запросе.
- Клиент не устанавливает обязательное для сервера правовое основание. Переданное злоумышленником `legalBasis` не легализует обработку и либо отклоняется как неизвестное поле, либо не является доверенным источником по утверждённому контракту.

Конкретные значения новой версии текста и точный полный JSON фиксируются при реализации. Нельзя утверждать, что текущий сервер уже принимает v2.

## 3. Серверные сведения о получении и цели

Предлагаемые отдельные метаданные после серверной проверки запроса:

| Поле/сведение | Семантика |
|---|---|
| `processing_purpose` | Например, утверждённая цель `trial_lesson_request`, соответствующая контексту этой формы |
| `legal_basis` | Для действительно необходимой обработки такой заявки: `152-FZ:6:1:5`, назначаемый сервером по утверждённой матрице целей, а не из клиентского обещания |
| `basis_policy_version` | Утверждённая редакция внутреннего решения о цели, необходимости и основании |
| `received_at_ms` | Время получения по часам сервера; не `Date.now()` клиента и не производное от клиентского `createdAt` |
| `request_schema_version` | Версия протокола, фактически присланная клиентом |
| `notice_version` и адрес уведомления | Какой информационный текст доступен для этого запроса; сервер проверяет известную редакцию и хранит её неизменяемый снимок отдельно от клиентского утверждения |
| Контекст запроса и событие получения | Связь `requestId`, страницы/школы, назначения формы и поступившего обращения. Не подтверждение личности или владения телефоном только фактом CAPTCHA |

Запись правового кода не заменяет содержательной необходимости операции. Основание для антиспама, облачного поручения, Telegram или иных целей не копируется без оценки из поля обычной заявки.

Серверное время не должно при обычном повторе незаметно перезаписывать ранее сохранённое доказательство получения. Нужно определить, фиксируется ли конкретная попытка или первое подтверждённое получение, и сохранить соответствующую семантику. Без атомарной защиты нельзя обещать точный порядок конкурентных первых записей. Технические поля не должны нарушать детерминированность повторной записи или проверку ReadRows.

Доказательства согласия появляются только в отдельном процессе, где согласие действительно получено. Не записывать `consent.accepted=true` для v2, не подставлять время согласия из времени получения запроса, не считать отсутствие рекламного отказа положительным согласием. Не добавлять токен CAPTCHA, секреты или полную переписку в журнал доказательств.

## 4. Обратная совместимость без остановки приёма

Последовательность для будущей реализации:

1. Утвердить основания и тексты, заполнить открытые сведения по получателям. Зафиксировать текущую версию и порядок отката, без выключения действующей формы.
2. На том же существующем обработчике предусмотреть раздельную строгую валидацию v1 и v2. В переходный период старые страницы и незавершённые попытки v1 продолжают приниматься; новые клиенты v2 не требуют поля `consent`.
3. Для v1 не объявлять автоматический `accepted:true` доказательством согласия. Сохранять исторический пакет как унаследованные технические данные с явной семантикой `legacy_unverified`, а основание обычной обработки определять по фактическому обращению и утверждённой матрице. Это не создаёт задним числом законного основания там, где его не было.
4. Подготовить хранение новых метаданных обратно совместимо: новые необязательные поля/формат, старые записи и читающие их участки не должны требовать значения, которого раньше не было. Конкретное изменение схемы YDB — отдельное согласование; здесь нет SQL-миграции, исполнения YQL, пересоздания таблицы или новой БД.
5. После проверки совместимого сервера обновить только служебный запрос формы, назначение/описание ссылки и тексты документов. Внешний вид, поля и название ссылки сохраняются. Публикация согласуется отдельно.
6. Дождаться определённого владельцем окончания переходного периода/кэширования, наблюдая версии и ошибки без логирования контактов. Убирать v1 только после подтверждения, что старые допустимые попытки не потеряются. Срок перехода сейчас не назначен.

**Откат:** сначала восстановить предыдущий клиент при сервере, понимающем обе версии. Откат на сервер, понимающий только v1, пока клиенты v2 ещё работают, недопустим. Метаданные и старые заявления не удалять ради отката. Кэширование и уже открытые вкладки учитываются отдельно.

## 5. Повторы, ключи и отсутствие ложных гарантий

Сейчас receipt зависит от `requestId` и хеша бизнес-пакета, включая прежние метаданные согласия. Простое удаление `consent`/смена канонизации может создать другую физическую запись и повтор уведомления для той же попытки.

- На первом этапе сохранить алгоритм и ключи v1, вместе с существующими отметками `sent:<receipt>`. Не переписывать все ключи или поля прежних заявок.
- Зафиксировать отдельную канонизацию v2: для повторов не должны влиять новый CAPTCHA-токен и вычисляемое время сервера. Перечень участвующих полей и версию алгоритма утвердить до реализации.
- Незавершённая попытка сохраняет свою версию протокола и один неизменяемый бизнес-пакет до результата. Нельзя незаметно переводить pending-запрос v1 в v2 между повторами. Новый запрос/новая инициатива не объявляется повтором только по совпадению телефона.
- Если понадобится повтор с одним ID между версиями, потребуется отдельная явная проверка старого receipt/отметки и сопоставление бизнес-содержимого. Нельзя выдавать общий ключ/двойную запись в таблицу за атомарную защиту: BulkUpsert + ReadRows не предоставляют compare-and-set. Строгая дедупликация конкурентных межверсионных запросов этим планом не гарантируется.
- Положительный ответ по-прежнему возможен только после подтверждённого сохранения; Telegram не вызывает повторное создание основной заявки. Наличие согласия или его отсутствие не должно менять это правило.

Минимальный безопасный переход не требует одновременной смены правовой модели, всех старых receipt и механики Telegram. Ограничения MVP о возможных повторах уведомлений после неопределённого исхода сохраняются и не скрываются.

## 6. Отдельный рекламный учёт

Он не добавляется в обычный endpoint автоматически. При дальнейшем общении/через CRM регистрируются самостоятельные события: контакт и его подтверждаемая принадлежность, каждый выбранный канал/сервис, отправитель, рекламная цель, два отдельных правовых акта при выбранной модели, тексты/редакции, событие пользователя, серверное время и ссылка на доказательство, срок, отзыв и объём отзыва.

Менеджер может внести сведения в CRM, но не создать за клиента согласие. Перед рассылкой проверяются актуальные ограничения и отказы. Поля `unknown`/`not_obtained`/отсутствие записи не превращаются в `granted`. Не назначаются реальные поставщики CRM или рассылки до их подтверждения.

## 7. Минимальные проверки будущей реализации

Только при отдельном разрешении на изменения: совместимость v1/v2, отказ без CAPTCHA и при неизвестных полях, сохранение/ответ, стабильный receipt при повторах, раздельность рекламного учёта, отсутствие ложного согласия, сохранение клавиатуры/скролла формы, безопасный откат. Эти проверки сейчас **не запускались**: текущая задача — документы.
