# Минимальный backend: BulkUpsert + ReadRows

Локальный кандидат, без развёртывания. Архитектура не меняется: существующие
Cloud Function `tochka-leads-api`, YDB `tochka-leads`, SmartCaptcha и Telegram.
Document API и YQL не используются. Предыдущие планы Document API не относятся к этому ZIP.

## Что делает обработчик

1. Проверяет существующий контракт `/leads`, Origin, контекст Gateway, поля и SmartCaptcha.
2. Создаёт детерминированную строку в `leads` через нативный BulkUpsert.
3. Читает её через ReadRows и сравнивает все записанные поля. Только после этого допускает HTTP 200 с `saved: true`.
4. При `DELIVERY_ENABLED=true` сразу отправляет Telegram в группу выбранного филиала.
5. Только после положительного ответа Telegram записывает и перечитывает отдельную отметку `sent:<receipt>` в `outbox`.

Задание уведомления не отделено от сохранения: неизменяемая строка заявки содержит
`status=notification_pending`. Отдельного промежутка между сохранением заявки и созданием задания нет.
Строка заявки не обновляется при отправке. Её `telegram_sent=false` и `status` — исходное намерение,
а не текущий статус доставки! Фактическое подтверждение — строка `sent:<receipt>` в `outbox`,
`shard=0`, `state=sent`, `lease_token` содержит Telegram message ID (не блокировку).
Старый SQL-обработчик очереди с этими строками запускать нельзя.

## Честные ограничения MVP

- Ключ заявки и `leadId`: `requestId:SHA256(канонического payload без captchaToken)`.
  Точный повтор, включая createdAt и данные согласия, сохраняет одну строку.
  Изменённый payload с тем же requestId создаёт отдельную версию, не HTTP 409.
- Нет условных записей и блокировок. Параллельные отправки или потерянный ответ Telegram
  могут дать дубликат уведомления. Потерянный ответ YDB может дать HTTP 503 после фактического
  сохранения; клиент повторяет исходный payload с новым CAPTCHA-токеном и прежним requestId.
- Ошибка Telegram не отменяет заявку: HTTP 200, `saved=true`, `notification=pending`.
  Это подтверждение сохранения, не обещание доставки менеджеру.
- Автоматического фонового повтора нет. Нужен приватный повтор по сохранённому receipt;
  без операционного контроля pending-заявка может остаться без уведомления.
  CAPTCHA обязательна. Ограничитель 5/IP/мин и 100/мин действует только внутри одного
  прогретого экземпляра функции: это не распределённая защита от спама.
- Не обещаются exactly-once, гарантированная доставка, автоматическое восстановление очереди
  или подтверждение прочтения менеджером. Новых сервисов и таймеров не требуется.

## Запуск после отдельного разрешения

1. Использовать Python 3.12, `index.handler`, ZIP `function-python312.zip`.
   Проверить SHA256SUMS. Установить достаточный timeout функции (60 секунд) и согласованный
   таймаут Gateway: сохранение, чтение и Telegram выполняются последовательно.
2. Использовать `environment.example`, существующий runtime SA и секреты из Lockbox.
   Endpoint и path жёстко ограничены подтверждённой `tochka-leads`.
   Разрешён только существующий префикс `tz_site_test_20261114_`: новых таблиц/миграций нет.
   `leads` и `outbox` должны иметь схему существующих тестовых таблиц (schema.yql).
3. Опубликовать отдельную тестовую версию без изменения существующих тегов.
   Сначала оставить `PUBLIC_LEADS_ENABLED=false`, `DELIVERY_ENABLED=false`.
   При проверке HTTP включать PUBLIC только в отдельно согласованном защищённом тестовом маршруте.
   Этот флаг разрешает обработку HTTP и сам по себе не предоставляет сетевой защиты.
4. Прогнать синтетическую заявку с настоящим SmartCaptcha через защищённый Gateway:
   две ветки, точный повтор, изменённый payload, отказ CAPTCHA, отказ хранения.
   В этом этапе новая версия в облаке ещё не проверялась; ранее в этой БД работали нативные
   BulkUpsert и ReadRows. Модельные тесты не доказывают облачную совместимость.
5. После отдельного разрешения на тестовое сообщение задать Telegram bot token и оба chat ID,
   включить DELIVERY_ENABLED в тестовой версии; проверить группы, ошибку отправки и повтор.
   Чаты выбираются только сервером: TELEGRAM_CHAT_KALUGA / TELEGRAM_CHAT_TROITSK.
6. Приватный повтор: файл retry.json содержит только `{"retryReceipt":"<leadId>"}`.
   IAM-авторизованный вызов конкретной тестовой версии:
   `yc serverless function invoke --id d4ep7jlje5la3g8ohd70 --tag <отдельный-тестовый-тег> --data-file retry.json`.
   Для этого тег должен быть отдельно согласован и назначен тестовой версии; существующие теги не менять.
   Этот JSON не является публичным HTTP-маршрутом. Функцию не делать публично вызываемой.
   `notification=sent` означает подтверждённый маркер; `pending` требует проверки конфигурации/повтора.
7. Для реального запуска отдельно согласовать рабочий префикс таблиц, домены SmartCaptcha,
   защищённую публикацию Gateway и переключение сайта. Проверить обработку персональных данных
   и локализацию. Этот кандидат ограничен тестовыми таблицами; сайт не изменён.

## Локальная проверка

`PYTHONPATH=backend/yandex-leads/tests python -m unittest test_bulk_mvp test_service test_launch`

Все тесты offline: RPC-клиент и Telegram заменены тестовыми объектами. Секреты, контакты
пользователей, облачные записи и реальные сообщения для этих тестов не нужны.
