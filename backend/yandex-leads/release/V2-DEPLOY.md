# Выпуск v2: код, миграция и удаление

Изменения реализованы в отдельной ветке. Команды ниже **не выполнялись в облаке**. Сайт и рабочие группы не переключались. Runtime — Python 3.12, index.handler; прежние база, функция, Gateway и Lockbox. Не использовать tochka-learning.

## Артефакты и порядок

- `leads-v2-python312.zip`, его SHA-256 и состав — в `leads-v2-manifest.json`.
- Пересборка: `python backend/yandex-leads/build_v2_release.py`. ZIP содержит только пять runtime-модулей и pinned requirements, без CLI/тестов/секретов.
- Миграция: `migrations/002-legal-metadata.json`, исполняется `admin.py` через SDK AlterTable, без компиляции YQL-запросов.
- Порядок строго **миграция → dual-сервер → клиент/документы**. Merge PR запустит существующую публикацию Pages: не merge до подтверждённого backend и разрешения владельца.

## 1. Аддитивная миграция — только после разрешения

Из `backend/yandex-leads`, Python с `requirements-admin.txt`, существующий авторизованный `yc` в PATH. Admin-only PyYAML нужен для YAML OpenAPI Gateway и не включён в ZIP функции. Планы размещать в закрытом каталоге оператора, вне публичного репозитория; на Windows проверить ACL каталога (POSIX mode 0600 сам по себе не заменяет Windows ACL).

```powershell
python admin.py schema-plan --plan C:\private\tz-schema.local.json
python admin.py schema-apply --plan C:\private\tz-schema.local.json --confirm <ПОЛНЫЙ_ХЕШ_ИЗ_ПЕРВОЙ_КОМАНДЫ> --audit C:\private\tz-audit.local.jsonl
```

Добавляются только nullable-метаданные к `tz_site_test_20261114_leads` в существующей **tochka-leads**. Название с test — историческое имя реально используемой таблицы, не разрешение очищать её. Старые данные не переписываются, TTL другой колонки не заменяется. При частичном сбое повторно получить schema-plan: не откатывать удалением колонок или таблицы. Изменение TTL не удаляет старые строки с NULL.

## 2. Версия функции

Создать новую версию существующей `tochka-leads-api`, Python 3.12, источник ZIP. Сохранить service account, ресурсы/таймауты, `--no-logging`, endpoint/DB/table prefix, переменные филиалов и существующие Lockbox bindings. Не использовать старый ZIP или старый Worker.

После миграции добавить `LEADS_SCHEMA_V2_ENABLED=true`, `LEADS_MAINTENANCE=false`. Сохранить `PUBLIC_LEADS_ENABLED=true` и `DELIVERY_ENABLED=true` **только для согласованного переключения рабочего тега**; приватная тестовая версия должна иметь `PUBLIC_LEADS_ENABLED=true` для проверки receive по IAM и `DELIVERY_ENABLED=false`, не иметь публичных invoker-прав и не быть подключена к Gateway. Публичность функции и HTTP-флаг обработки — разные настройки. В обоих случаях серверная SmartCaptcha обязательна.

Обязательные прежние секреты: SMARTCAPTCHA_SERVER_KEY, RATE_HMAC_KEY, TELEGRAM_BOT_TOKEN, TELEGRAM_CHAT_KALUGA, TELEGRAM_CHAT_TROITSK. Использовать актуальную согласованную версию существующего Lockbox, не копировать значения в CLI-аргументы, ZIP, GitHub или отчёт. Новых секретов не требуется.

Публичный route `/leads`, контекст `website-leads-v1` и Origin остаются прежними. Сервер принимает v1/v2; новый клиент отправляет только v2. Фамилия пустая допустима только в v2. Версия уведомления — `2026-11-14-v2`. Автоматическое accepted для новых заявок не создаётся; v1 помечается legacy_unverified.

`received_at_ms` — серверное свидетельство подтверждённой попытки. Повтор использует сохранённые метаданные, а не продлевает хранение. При одновременных первых записях без CAS точный порядок «самого первого получения» не гарантируется; рассогласование чтения даёт ошибку, не ложный успех. Старые receipt и sent:-ключи не мигрируют; изменённый пакет с тем же requestId по-прежнему отдельная версия. Exactly-once Telegram не обещается; сохранённый pending не теряется, используется прежний приватный повтор.

Перед рабочим тегом нужен разрешённый приватный smoke на синтетике: сохранение/чтение v1/v2, nullable-типы, TTL в реальном YDB. Нельзя считать offline fake-client тест доказательством этого. Реальные тестовые сообщения в рабочие группы не отправлять: тестировать sender заглушкой либо оставить DELIVERY_ENABLED=false; локальные тесты отдельно проверяют серверный выбор обоих чатов.

## 3. Публикация клиента и документов

Только после успешной серверной проверки и разрешения владельца — merge/Pages. Секреты браузеру не передаются. Нет новых галочек, дизайн/маска/клавиатура неизменны, поле фамилии сохранено без required, ссылка по-прежнему «Ваши данные в безопасности». Старый #consent работает как объяснение новой модели. Рекламные проекты остаются в legal-review для отдельного процесса.

Документы не утверждают оформленность неизвестных договоров/уведомлений или наличие лицензии; домашний адрес не добавлен. Это не заменяет необходимых действий владельца по внешним потокам и доступу.

## 4. Хранение и существующие данные

Новые записи и sent:-копии получают календарный предел три года по серверным часам и TTL `purge_at_ms`. Использование/доставка просроченной записи блокируются и до физического завершения TTL. Повторы не меняют срок. TTL асинхронен: физическое уничтожение проверяется отдельно, не обещается точная миллисекунда.

Старые строки с NULL не считаются охваченными TTL автоматически. Для каждой существующей заявки применить ограниченный retention-plan с реальным исходным событием; при исходном клиентском времени указать legacy_received, не выдавать его за серверное. Содержательный контакт/фактическое завершение занятий фиксируются отдельно, не как любой updated_at:

```powershell
python admin.py retention-plan --receipt <UUID:HASH> --anchor 2026-11-14T12:00:00+03:00 --reason meaningful_contact --plan C:\private\tz-retention.local.json
python admin.py retention-apply --plan C:\private\tz-retention.local.json --confirm <ХЕШ> --audit C:\private\tz-audit.local.jsonl
```

Допустимые причины: meaningful_contact, training_ended, legacy_received. Временная точка — фактическое событие, не пример из команды. Законное исключение по конкретному обязательному документу вести отдельно; не продлевать всю заявку флагом legal hold. До включения срока убедиться, что не удаляются необходимые активные сведения без основания. Для контроля Telegram-копий запускать обзор до истечения TTL, см. следующий раздел; автоматический TTL YDB не удаляет сообщение в Telegram.

## 5. Досрочное удаление и просроченные записи

```powershell
python admin.py plan --receipt <UUID:HASH> --plan C:\private\tz-delete.local.json
python admin.py plan --expired --limit 5 --plan C:\private\tz-expired.local.json
# Для заблаговременного разбора сообщений: --expired --within-days 7
```

План включает все версии одного requestId и sent:-копии, fingerprints и ссылки на сообщения, без ФИО/телефонов. Максимум 20 выбранных заявок / 40 строк; --all нет. До применения просмотреть защищённый план, проверить смысл досрочного удаления и исключения. Если связанная версия не просрочена, выборка expired отказывает и требует отдельного решения. Планы удаления действительны один час; изменение хотя бы одной строки требует перепланирования. Сам план содержит связанные идентификаторы, это не анонимный публичный документ.

Для применения требуется короткое отдельно согласованное окно обслуживания **этой функции**: версия нового кода с LEADS_MAINTENANCE=true на действующем Gateway-теге. Она возвращает 503 без приёма, не выполняет приватный retry. CLI проверяет Gateway, IAM-вызов adminStatus, active version и её окружение, ожидает максимальный timeout перечисленных версий плюс пять секунд, повторно проверяет тег/маршрут. В окне запрещены ручные вызовы других старых версий; IAM-доступ только уполномоченному оператору. Планирование не требует окна; применение требует. Это окно не включалось этой разработкой и не является постоянным отключением Telegram.

```powershell
python admin.py apply --plan C:\private\tz-delete.local.json --confirm <ХЕШ> --audit C:\private\tz-audit.local.jsonl
python admin.py check --plan C:\private\tz-delete.local.json --confirm <ХЕШ> --audit C:\private\tz-audit.local.jsonl
```

Сначала подтверждается replay-guard, затем очищается содержимое указанных строк и ставится ближайший TTL. При частичном сбое оставить режим обслуживания и перепроверить состояние, не объявлять успех. Не перепланировать очищенные строки как новые контактные заявки. Guard блокирует старую попытку в течение 48 часов (дольше окна допустимого старого payload); это минимальный связанный идентификатор, не анонимная вечная блокировка.

`check` возвращает код 2, пока данные либо временный guard ещё существуют; код 0 и physical_delete_confirmed только после исчезновения всех выбранных строк и guards по ReadRows. Нельзя стирать guard вручную ради зелёной проверки. TTL не обещает мгновенную физическую очистку. После завершения операционного окна восстановить обычную версию нового dual-кода; не терять поступившие ранее заявки и markers. Проверять сроки/исключения статьи 21 и фактическое удаление резервных копий с провайдером; это не реализуется удалением только активной строки.

## 6. Telegram — исполнимая процедура без отключения уведомлений

До потери ссылок из YDB сохранить защищённый план; он содержит branch/message_id для уже подтверждённых сообщений. Если прежняя доставка завершилась неопределённо, сообщения без записанного ID нужно дополнительно найти в группе по ID заявки: отсутствие sent: не доказывает отсутствие сообщения.

Для сообщения моложе 48 часов уполномоченный оператор может выполнить:

```powershell
python admin.py telegram-delete --plan C:\private\tz-delete.local.json --confirm <ХЕШ> --audit C:\private\tz-audit.local.jsonl
```

Нужны существующие Telegram-переменные в защищённом окружении оператора; из плана chat/token не берутся. Код использует только deleteMessage и серверную branch→chat привязку, не отправляет новое сообщение. На ошибке подтверждение не записывается; ошибка/лимит API не означает удаления. Для старого сообщения — администратор открывает соответствующую группу, находит указанный message_id/заявку и удаляет сообщение для участников; проверяет отсутствие и управляемые пересылки/выгрузки. Затем:

```powershell
python admin.py telegram-manual-confirm --plan C:\private\tz-delete.local.json --confirm <ХЕШ> --audit C:\private\tz-audit.local.jsonl
```

Последняя команда — только запись утверждения оператора после реального действия, не независимая API-проверка. Не обещать удаления неконтролируемых чужих копий. Журнал содержит время, хеш плана, вид операции и счётчики, без имён/телефонов/raw receipt; доступ и сроки журнала/актов ограничиваются отдельно. Для автоматизированного уничтожения оформить акт и необходимые подтверждения, не включать полный пакет заявки заново.

## Откат и доступ

Откатить клиент раньше backend, оставив dual-сервер для старых v2-вкладок. Не возвращать v1-only код и не удалять добавленные колонки; не восстанавливать старый snapshot поверх новых заявок. При проблеме TTL отключение/изменение — отдельное разрешение, а не слепой rollback таблицы. Старый Cloudflare Worker не переключается автоматически.

CLI требует существующих IAM-прав на tochka-leads: чтение/запись, AlterTable для миграции, чтение Gateway/версий и private function invocation для окна. Не расширять права runtime-сервисного аккаунта для CLI; выполнять операторской учётной записью. Нет публичного admin HTTP-маршрута. Секреты не выводятся. До разрешения не выполнять никакую команду apply/telegram-delete в облаке.
