# Выбранный вариант: Document API, одна атомарная запись

Реализован локально в prepare/document-api-intake. Облачные ресурсы не менялись.
Приложение не отправляет YQL и не использует BulkUpsert. Новый runtime содержит
document_api.py / document_store.py вместо SQL-адаптера. Запуск и Telegram выключены.

## Почему этот вариант

| Вариант | Решение |
|---|---|
| BulkUpsert + предварительный ReadRows | Не подходит: между чтением и безусловной записью есть гонка, повтор может перезаписать принятую заявку/состояние доставки |
| Другой YQL/Query/Scripting маршрут | Не выбран: повторно исследовать известную 400090 не требуется |
| Document API: conditional PutItem + strong GetItem | Выбран: условие создания и изменение документа атомарны; IAM Bearer поддержан официально |

Одна новая **документная таблица в существующей tochka-leads**, не новая БД/сервис.
Первичный ключ pk. Заявка: pk=lead:<requestId>. В том же документе находятся
неизменяемый payload_json, хеш, lead_id и notify_state/lease/attempts/telegram_sent.
Рядом в этой таблице — минутные счётчики и курсор обхода. Нативные SQL-таблицы
tz_site_test_20261114_* не изменяются и не переиспользуются как Document API-таблица.

## Гарантии и окна сбоя

1. **Создание:** PutItem с attribute_not_exists(pk). Тело заявки и pending-событие —
   один документ/одна атомарная операция. Окна «заявка есть, задания уведомления нет» нет.
2. **Подтверждение:** после записи обязательный GetItem ConsistentRead=true.
   При потерянном ответе PutItem успешное сохранение подтверждается только этим чтением.
   Если чтение не подтвердило сохранение — никакого HTTP-успеха.
3. **Повтор:** тот же requestId/хеш/содержимое возвращает существующий lead_id.
   Другие данные с тем же requestId — 409. Повтор не переписывает документ и
   не возвращает уже отправленное уведомление в pending.
4. **Конкуренция:** все изменения — полная замена документа с условием version=прочитанная
   версия и attribute_exists(pk). Если другой экземпляр опередил — перечитать и повторить.
   Безусловных замен/BatchWrite/BulkUpsert и обходного SQL-fallback нет.
5. **Доставка:** только владелец подтверждённого lease отправляет Telegram.
   Lease и номер попытки записываются до отправки; истечение lease восстанавливает работу.
   Новый lease имеет новый token; старый обработчик не может завершить чужую попытку.
6. **Успех Telegram:** sent, telegram_sent и message_id фиксируются одной условной заменой.
   Если ответ фиксации потерян, следующая проверка видит sent либо сохраняет возможность повтора.
7. **Ошибки:** сеть/5xx — задержка; 429 — не раньше retry_after; 400/401/403 и 12 неудачных
   попыток — attention. Заявка и задание остаются в документе для ручной обработки/replay.
   Ни ошибка, ни исчерпание попыток не удаляют данные.
8. **Обход:** Scan с пагинацией и долговечным CAS-курсором. Пустая страница после фильтра
   не означает конец. Курсор доходит до конца и начинает новый проход; сдвиг курсора
   не подтверждает/не удаляет уведомления. Падение до отправки откладывает pending до
   следующего прохода, а не теряет событие. Производительность должна покрывать входящий поток.
9. **Срок хранения:** TTL expires_at задаётся только счётчикам. У заявок/очереди этого
   атрибута нет: pending/attention не исчезают из-за TTL. Удаление заявок — отдельная политика.

Как и раньше, потеря ответа Telegram после фактической отправки может привести к
повтору уведомления: sendMessage не имеет идемпотентного ключа. Exactly-once Telegram
не обещается. Дубликата заявки в базе нет; requestId есть в сообщении для сверки.

## Что доказано локально

Тесты используют исполняемый атомарный **контрактный макет Document API**, а не SQLite
и не симуляцию «успешной отправки» в приложении. Проверяются реальные HTTP-параметры,
условия записи, strong-read, одновременные отправители, сбои до/после commit, потеря ответа,
lease fencing, retry_after, attention, пагинация и восстановление процесса.
Это проверка алгоритма при документированных гарантиях API, **не доказательство работы
Yandex Document API в текущей облачной БД**. По публичным документам нельзя установить,
затронута ли внутренняя реализация Document API той же серверной причиной 400090.
Поэтому следующий шаг — один короткий smoke именно условных операций, без новой диагностики YQL.
Если сервер не выполняет условие/strong-read, приём не включать; небезопасного fallback нет.

## Конкретный план запуска после отдельного разрешения

1. Через Document API CreateTable применить create-document-table.json только в
   существующей tochka-leads. Таблица tz_site_test_20261114_documents, HASH key pk.
   Нового сервиса, ключей доступа, БД, Gateway или SWS не требуется.
   При необходимости document-ttl.json включает TTL только счётчикам.
2. Выполнить приватный smoke из tests/test_document_live.py через существующую авторизацию yc.
   Он не создаёт таблицы, не отправляет Telegram и работает только с фиксированными
   endpoint/table. По умолчанию выключен. После разрешения:
   PYTHONPATH=backend/yandex-leads/tests
   YDB_DOCUMENT_SMOKE_ALLOW=I_APPROVE_SYNTHETIC_DOCUMENT_WRITES
   python -m unittest test_document_live -v
   Критерии: два одновременных create дают один receipt; конфликт — ошибка;
   потерянный ответ восстанавливается strong-read; две lease одновременно не выдаются;
   старый lease не подтверждает sent. Никакого возвращения к диагностике 400090.
3. Выпустить отдельную **приватную** тестовую версию Python 3.12 на tochka-leads-api,
   не перемещая существующие теги. Использовать release/function-python312.zip.
   Тестовый entrypoint: private_document_test.handler (обычный runtime: index.handler).
   PRIVATE_SYNTHETIC_TEST_MODE=true разрешает только строго фиксированные синтетические
   имя/фамилию/телефон и только таблицу tz_site_test_20261114_documents.
   LEADS_STORAGE_BACKEND=document; YDB_DATABASE_LABEL=tochka-leads;
   YDB_DOCUMENT_TABLE=tz_site_test_20261114_documents;
   YDB_DOCUMENT_ENDPOINT=https://docapi.serverless.yandexcloud.net/ru-central1/b1gs93r1fhsuparnmrba/etntmjbnguvsu5l8bv3s
   CAPTCHA/HMAC — существующий тестовый Lockbox; IAM — привязанный SA, токен из metadata.
   Новые постоянные ключи не создаются. PUBLIC_LEADS_ENABLED=false, DELIVERY_ENABLED=false.
   Неаутентифицированный вызов обязан получать отказ IAM до запуска handler.
   Через yc invoke передать только requestId, createdAt, branch и captchaToken,
   полученный отдельным localhost:8767 виджетом. Никаких полей реального человека.
   Harness проверяет действительный ответ SmartCaptcha status/host; пустой host,
   production host и добавленные поля отклоняются. Он не подменяет CAPTCHA.
4. После успешного smoke и отдельного разрешения на реальный запуск — включить
   периодический доверенный обработчик этой функции, проверить retry/attention на синтетике,
   затем открыть согласованный API и переключить endpoint формы. Публичный Gateway,
   Telegram, production/main/DNS/Cloudflare сейчас НЕ меняются.

Для старта не требуется переноса старых SQL-таблиц или работоспособности /lead.
Реальные данные до отдельного допуска не принимаются. Возобновление attention — только
приватной администраторской CAS-операцией после устранения причины, не публичным URL.
